## 3. Tunnels
* **Tunnel manager**: health every minute (units on both sides, GRE interface, 20 pings, forwarded ports, one HTTP request through the tunnel) plus one HTTP request through the first forwarded port from the server itself and from another Iran server (the users' path): data decides, the ping over the GRE link only matters when no data passes; with a reason per state and hysteresis against flapping - a link that failed 3 of the last 10 checks stays *degraded* ("the link flaps") even when this check passed, so users' cuts are never shown green; More window with quality, ports, rebuild, history, remove; detect tunnels already on the servers and adopt them.
* **Create**: backhaul-over-GRE (preflight of both servers, free control port, path-MTU measurement, kernel tuning, hold test, rollback on failure), plus BackPack, BackPack Direct, Paqet and Chisel engines; "choose for me" ranks the Iran servers for the foreign one. Before a build the ports are checked: a port already used on the chosen Iran server stops the build with a sentence (choose another server or port); a tunnel that already carries the port to the same foreign server can be replaced (removed first), and the CDN records that served only it follow the new Iran server through the failover.
* **Tunnel test**, in two tabs. *Tunnel test*: builds a temporary tunnel per chosen transport, measures latency / jitter / loss / download, compares, removes it; Advanced lists the transports; the live log stays on the page. *Network advisor*: for an existing tunnel, tests every type between its two servers and says which is best today; "Use" replaces the tunnel with that type (same name and ports, the old type comes back if the new one fails).
* **Core update**: backhaul / Xray version on every server against the newest release, verified download.
* **DNS · IP switch**: the records of every domain of your DNS accounts (several ArvanCloud accounts and Cloudflare under one list) like the account's own page - Type · Name · Value · TTL · Cloud - with add / edit / delete of A records, a Restore for every change, the failover plans and the connection status of each account. The automatic IP switching is paused while it is tested; a record can always be changed by hand.
* **Tunnel Doctor** (tunnels only), in two tabs. *Working now*: the tunnels that are down, degraded or lossy, what the Doctor is doing with each, Diagnose (both sides, the route, GRE, control port, data path), Fix with AI (restart → rebuild → a new GRE link → another type, and the move to another Iran server through the IP switch), Fix all, Explain with AI; the CPU-on-the-cores card (RPS for a server whose packets sit on one core); the History of the problems and whether they were solved. *Analyst*: what the history says - a profile of every tunnel (availability, outages and how long they last, normal latency and whether it is rising, weak hours, verdict), the tunnels at risk, outages that come together on tunnels of one server, what fixes what (how often each step healed which cause), and the servers at the peak hours (idle, redundant, busy) with a look at each one's own network and a one-click fix of the kernel settings. The smart repair asks the Analyst before it climbs: a step that failed again and again is skipped. Auto-repair with limits (2 plain restarts per tunnel per hour, a smart repair every half hour, never when a server is off, never in a storm).

## The layered look, second phase (1.69.291)

Three additions (the owner, 2026-11-19, «بریم فاز بعدی»). (1) The quality job (`quality`, the latency, jitter and loss of every tunnel, every 30 minutes) took 156 seconds one tunnel after the other on the live fleet - the only background test
that was fully serial (the rest already run their servers in a pool, some on purpose slowly): now every Iran server is a lane (its tunnels one after the other, so a small server is never asked for two measurements at once) and six lanes run at once.
(2) A tunnel that the layered look restarted and that STILL resets new connections two looks later gets another type built beside it without a cut (`pathprobe.escalate`: the best other type that works on the pair and is not known to be unsteady,
the same swap as every automatic change, no speed gain asked for), once in 24 hours per tunnel, never a protected one, not while more than a third of the looked-at tunnels have that verdict at once. (3) The tunnel window has a Layers row: what each layer
answered (fresh TLS handshakes through, out of those tried) and the verdict. Not built: a DNS layer (a name that points at a CDN or rotates on purpose would be accused) and the configs behind a CDN name.

## The layered look: where is the problem (1.69.290)

When the users of a config suffer, the Doctor used to ask one question - how fast is the tunnel - and a speed test of one big connection hides a tunnel that stalls or resets NEW connections. On 2026-11-19 a config answered 24-85 % of the probe's
tests for two days while its foreign server, its DNS and the Iran network to its Iran server were all fine; only the tunnel instance reset new connections (one restart cured it). Now a job (`pathprobe`, every 30 minutes) looks at every layer
between a user and the internet, lightly and in parallel: for the user port of every config that rides a tunnel, N fresh connections - the TCP connect time and the TLS handshake with the config's own SNI, nothing sent after it, a few kilobytes
in all. Three layers: the NODE (from the panel's host, abroad: the foreign server's inbound port, no tunnel, no Iran network), the TUNNEL (on its Iran server itself, 127.0.0.1: the tunnel and the node behind it, no network in between; one ssh call
per Iran server, its ports in threads there) and the PATH (from other Iran servers to the Iran server's own address - only for a tunnel whose users suffer while the first two are fine, and only a failure of every vantage counts). The verdict is the
first layer that fails - `node`, `tunnel`, `path`, `ok` - kept in the record of the tunnel (`layers`) and changed only after two looks in a row; a layer that was not measured accuses nobody, and when most nodes fail at once from the panel's host
the panel's host is the blind one and no node is judged. What is done: a tunnel whose settled verdict is `tunnel` (the node answers, the tunnel resets) is restarted on both ends - the same action as the Restart button - at most once in six hours, only in the
modes fix and move, never a protected one, never while the Doctor's own affairs wait; and a foreign server whose node does not answer for two looks in a row gets a small tag next to its name (the Tunnels table and the server's window) with an event,
which goes when the node answers again. The volume (about 100 MB a day for thirty configs) is counted in the day's volume of the Doctor's tests. The rule of 1.69.288 (a better type beside a tunnel whose users suffer) now also fires when the Doctor's memory calls
the type the tunnel runs as UNSTEADY and no faster type is known: the best other type that works on the pair is taken, and the swap is not asked for a speed gain over a number that hides the fault.

## The duplicate sweep does not side with the old tunnel (1.69.289)

When a move builds a tunnel beside the old one and the users still hold the old one, the two serve the same ports of the same foreign server and the duplicate sweep (`janitor`) judges the group: the keeper is the busiest tunnel that is up AND
measured. 12 of 26 tunnels of the owner's panel cannot be measured - chisel, BackPack wss / wssmux / stealth / tcpmux have no traffic counters. So when the new tunnel was one of those, the old one was always the keeper: on 2026-11-18 the sweep
pointed the DNS name that the Doctor's own move had changed BACK at the old tunnel, and the new tunnel was neither keeper nor extra for good (it stayed called -mv). Now a tunnel that cannot be measured but is up and has a DNS name tied to it is the keeper
(when no measured tunnel of the group is tied to a name), no name is ever pointed at a tunnel while the use of any tunnel of the group is not known (`consolidation_target`), and the old tunnel goes when it is quiet for three hours and no name is tied
to it - after which the -mv name of the new one is dropped by the tidy round. Two tunnels that cannot be told apart are still told once a day and nothing is removed.

## A tunnel whose users suffer gets a faster type beside it (1.69.288)

The Doctor grades every tunnel by what its users really get (`userq`: the share of the probe's tests that answered, the ping against the config's own week, the speed). When the grade falls to poor or bad it looks and says where the problem is -
and when the tunnel itself is healthy (bandwidth, loss, delay, servers) it said "beyond the tunnel" and did nothing. On 2026-11-17 a config on a tunnel built that morning answered 51-75 % of its tests for a day, the tunnel had no failed check and a
steady delay, and the Doctor said so three times. Now, when the grade has been poor or bad for three hours, the Doctor's own look still says "beyond the tunnel" (not down, not slow, no loss, no busy server) and its memory of the pair knows a clearly faster type
(`bandwidth._faster_row`: at least five times what the tunnel gives and at least 20 Mb/s) that is not known to be unsteady, that type is built beside the tunnel and the users go over without a cut - the same swap as every automatic change of type (`doctor._run_retype`
with auto, `swap.beside`: speed test through the new tunnel, handover, the old tunnel removed last, `retypewatch` puts the old type back when the users leave). The rails: the modes fix and move, nothing while a failover or a mass disruption is on (`quiet_now`),
two swaps at once, the day's volume of tests, once in 24 hours per tunnel, a protected tunnel never, and nothing when more than a third of the graded tunnels suffer at once (then it is the probe or the foreign side). A tunnel is tried at most every six hours.
What stays: a type that only tested fast is not proof - the swap measures it through itself again and refuses it when it is not clearly better. Not proved on a real tunnel.

## The failovers of one outage do not collide (1.69.287)

When several Iran servers are cut or off in the same minute, every one of them is planned and started at once, and their tunnels go to the Iran servers that are left. Two things made some of those failovers end "not ok" (2026-11-17, four
Iran servers cut from abroad at once; two of the four failovers did not finish): (1) the target of a plan was the best ranked server with the tunnels already on their way counted, but not their PORTS - two tunnels that listen on the
same port went to the same server and the second build stopped with "port 8072 is already in use on the Iran server"; (2) two plans that built tunnels between the same two servers (the dead servers carried tunnels to the same foreign server) - the
second build was refused at once with "a tunnel between these two servers is already being built" and the tunnel it had taken off the dead server was put back dead. Now `failover.assign_target` passes over a server where a port of the plan is taken
already - by a tunnel of the panel there, or by a tunnel on its way from another plan of the same minute (`coming_ports`) - for the next server that can carry all the tunnels (`pick_free_target`), and the story says so (`ports_note`); when no server has
them free the best ranked one stays the target, as before. `autopilot._build_kind` waits for a busy pair (every 15 seconds, up to ten minutes) instead of failing. A move the operator started (`strict`) already proved its ports free; this is the same
for the automatic one, from the panel's own record (the listening ports are not read over SSH: a failover must not wait for that).

## A Servers folder is a wall (1.69.286)

A Servers folder that holds an Iran server AND a foreign server is a private folder (the owner, 2026-11-18, two servers of a friend's panel kept in a folder of their own: nothing of the fleet may be tunneled onto them, and the Doctor must watch them). The servers of a
private folder are chosen only for tunnels between servers of that folder: the smart choice of Create tunnel, the Doctor's resource, quality, capacity and return moves, the temporary test tunnel of a cut tunnel, a plan with a target the panel chose, the AI commander's move, the
relay strand, the outbound relay the panel suggests and the Bale watch list all leave them out. Their Iran servers also run none of the panel's own probes (the vantages, "filtered in Iran?", the config and TCP reach, the SSH jump, the site and SNI checks, the ping round, the loss locator);
the fleet still looks at them, so the Doctor watches them like any other server. The fleet itself (Iran servers in one folder, foreign servers in others) is not private: nothing changes for it. A choice made by hand (the Move button, Create tunnel with an Iran server picked)
stays the owner's. The rule lives in `nikatel/services/folders.py`.

## A tunnel called -mv gets its own name when the old one is gone (1.69.285)

A move builds its new tunnel beside the old one under a temporary name (`<name>-mv`, or `-mw` when the old one already carries `-mv` on the servers) and gives it the old name when the old tunnel is removed. Two things left the temporary
name on a tunnel for good: the old tunnel is kept when users still hold it half an hour after the DNS changed (the move says so and skips the rename), and the janitor can remove the plain-named tunnel later as "an extra copy" of the
`-mv` one. On 2026-11-18 three tunnels of the owner's list ended in `-mv`; nothing renamed them afterwards, because `tidy_names` only followed Iran server names. Now the tidy round (every ten minutes, never while a failover runs or waits, never
in a read-only panel) also renames a tunnel called `<name>-mv` / `-mw` when it is older than the move's own half hour, the name before the suffix is one the panel made (`<foreign>-<iran>` of any Iran server, with or without `-N`, or its first
eleven characters: a long name is cut before the suffix) and the tunnel it replaced is gone - the name is free. It takes the name the panel gives on the Iran server it runs on, unique among the tunnels. A name chosen by hand, a standby, a protected
or switched-off tunnel and a name that is not a panel name are left alone. The configs that name it, the alert mutes, the standby and the Doctor's ledger follow; what the servers know it as does not change.

## A timeout is not a verdict on the route (1.69.284)

A build step of a test that stopped with `timeout after 30s` (the panel's ssh gave up waiting for a server) was kept in the Doctor's memory of the pair as a plain FAILED kind, and the pair left that kind alone for 14 days. On 2026-11-16 ten kinds
on three pairs were blocked that way - three of them on a new server within the hour they were first tried - without anybody having judged the route. `knowledge.LOST_MARKS` now holds `timeout after`: such a kind is "not tested" (the same word as a server that went off), it is
asked again after a day (`TOOLS_RETRY`), it leaves no line in the history of the kind, and what was kept before is read again as "not tested" at once (`verdict`). What the route itself said - a link that answers and loses its packets, inner addresses that cannot ping - stays a failure.

## The volume of the Doctor's tests, cut at its two sources (1.69.282)

With the ten-day rhythm the day's volume still read 53 GB on a mean (the budget is 30): the night of 2026-11-16 filled 11 GB in its first 44 minutes. Two things made it, and neither was a count of tests the owner wanted to lower.
(1) **The pair speed test had no byte cap**: eight connections for four seconds each way, then one connection - on a pair that carries 2 Gb/s that is up to 2 GB a test, and a new server brought tests by the dozen. The speed tests the Doctor asks for by itself
(the verify survey, `tunnel_test.CAPPED_SOURCES`) now stop a stream by BYTES too (`probe_run`'s `BYTES` for the download, the new `UBYTES` for the upload): eight connections pull 24 MB and push 20 MB, the one connection 96 MB and 32 MB - 480 MB a test at the
most (1.1 GB on a line of 1 Gb/s before). A line under about 0.5 Gb/s never reaches the cap (the four seconds end first), so its numbers are what they were. Measured on two standby tunnels (1.07 and 0.6 Gb/s) before it was shipped: the eight connections read the same
as the whole four seconds; a short upload (12 MB) read 20 - 28 % low and a short single connection (48 MB) 15 % low, which is why the caps are what they are. A test the owner asks for (Compare, Test now, the Smart test, a new tunnel's first measurement) and a repair's
candidate tests are never capped.
(2) **The poor-score rule measured a far line every ten minutes for ever**: the quality score comes from the delay, so a line of 170 ms is under 40 whatever it does, and every tunnel under 40 got a speed test ten minutes after the last one (105 a day on 8
tunnels, one of them alone 33). Now the test goes after ten minutes only when the tunnel is NEWLY poor - it was not poor at its last test (the test keeps the score it had: `bw["q"]`), or its score fell 15 points since - and every six hours when it was poor at its last test too (`bandwidth.poor_after`).
And the volume is no longer one number: every count carries the NAME of what asked for the test (`testbudget.purpose`: `bandwidth`, `pair-survey`, `pair-test`, `new-tunnel`, `tunnel-test`, `tunnel-speed`) - the bytes and the number of tests of today, and the last days with their names (`days_by`) - the
tooltip of "tests today" on the Doctor's page lists them.

## The free quality signals (1.69.281)

With the speed tests asked once in ten days, the quality between them is read from what costs no byte. Every five minutes one light command per Iran server (`tcp_health`) reads, from the kernel's own counters of the tunnel's TCP sockets (`ss -tin`: bytes sent,
bytes sent AGAIN), how much of what the tunnel sent it had to send again - a clean line about 0.1 %, measured on four live tunnels; a line that loses packets several percent. And the speed the users get through the tunnel (the checks' counters) is compared with the SAME HOUR
of the last days. When the resend share of the last hour is 2 % or more in two looks in a row, or the users carry under half of their usual at this hour for two looks (their usual at least 10 Mb/s, from two different days), the signal asks the bandwidth job for a speed test of that
tunnel now - at most once in 12 hours per tunnel, only while the day's volume of the Doctor's tests allows routine tests - and writes why (the record `fl`, an event). The speed test is the confirmation and decides, by the rules it always had. A signal alone changes nothing.

## One speed test every ten days (1.69.280)

The speed tests were the volume of the Doctor's own tests (the day's use of 38 - 84 GB against a budget of 30): a kind of a live pair got three of them in a week (`VERIFY_TESTS`, one a day at most), and the bandwidth job measured every
tunnel every four hours. The owner (2026-11-15): "one speed test every 10 days - do not reduce the tests - optimize only the factor that makes the volume". Now NO test is dropped: every kind is still tested, the pings, the latency
tests of the night survey and the quality job run as before; only the SPEED part of the routine is asked once in `testbudget.speed_every()` (`speed_days` of the settings document `testbudget`, 10 by default, between 1 and 60) - per kind of a
pair in the verify survey (`knowledge.verify_kinds`: its last speed test, from any source, is 10 days old or it never had one) and per tunnel in the bandwidth job (`bandwidth.every()`). What something asks for does not wait: a tunnel never
measured, a drop, a very slow tunnel, a poor quality score, the repair's own candidate tests and the owner's own tests. The stability of a type is still known: three speed tests ten days apart fall in the month the rule looks at.

## An L2TPv3 leftover is removed by its session (1.69.278)

A link of the L2TPv3 kind cannot be removed with `ip link del`: the kernel keeps the device while its SESSION exists. The sweep of test leftovers (`purge_test_leftovers`, before every tunnel test) and the clean-up of a link probe (`link_probe_clean`) deleted the scripts and the device and only the L2TP tunnels without a session - so a cut-short L2TPv3 probe left its session, a device that was DOWN and its firewall rules on the Iran server for ever (one was found by hand on 2026-11-15 and cleaned). Now both delete the SESSION of a `lp-*` / `test-*` device first (the tunnel left empty goes next; the probe's clean-up deletes the tunnel only when no session is left in it) and remove the firewall rules whose comment is the exact tag of such a link (`nikatel-gre-lp-*`, `nikatel-gre-test-*`). A live tunnel is never named like that, so none is touched.

## A new tunnel gets its first measurement even on a day the tests filled (1.69.276)

The row of a tunnel shows a dash (and "measuring") until its first speed test. The Doctor's own tests (surveys, moves, verifications) have a daily budget (`testbudget`); the first test of a tunnel with no number was allowed until the day had used 150 % of it - and on a day at 184 % a tunnel rebuilt that afternoon kept its dash until the next Tehran day. Now, over 150 %, such a tunnel still gets up to 3 first tests a day, and all the tunnels together up to 60 (a first test moves 120 MB at the most, about 7 GB in all), so a test that fails again and again, or a loop that builds new tunnels again and again, still has an end. Tunnels that were measured before and dropped still wait for the next day when the whole budget is used. The page's test-volume card says how many first tests were made over the share (`firsts`).

## The Doctor clears ghost failed units by itself (1.69.275)

The unit file of a test tunnel can be gone while systemd keeps its `failed` state (`not-found failed`): nothing is left to remove, so the orphan sweep never saw it - and the builder refused every tunnel test and survey of that server ("has failed tunnel units") for days. The orphan sweep (every half hour, every server) now reads those ghosts in the same look and clears them with the reviewed action `ghost_reset` (`systemctl reset-failed`, only units of the tunnel engines whose LOAD is not-found and that are failed; a unit that exists is never touched, nothing is stopped or removed). One event a day per server says what was cleared; in the mode off, in a storm and in read-only nothing runs, like the rest of the sweep.

## A blip is not told (1.69.273)

About sixty «🔴 DOWN» messages a day came to Telegram, each followed by its «🟢 UP again» a minute later: a config's test from a data centre misses now and then (the monitor needs two tests in a row, about a minute), a tunnel cut for fifteen seconds is carried by its standby, the panel host cannot always reach a server that is on. Now every KIND of thing waits at least its own time before its DOWN goes out: config 5 minutes, tunnel 1 minute, server 90 seconds, node 2 minutes (`down_seconds_by_kind` in the alert settings; the base `down_seconds` stays the floor, so a longer base wins). A fault that lasts longer is told as before, with the clock counted from when the checker saw it; a blip that comes back sooner says nothing, neither DOWN nor UP.

## A port that does not answer is not a port that carries nothing (1.69.272)

The Doctor asks every forwarded port of a tunnel, on its Iran server, whether a connection to it stays open (it carries) or is closed at once (nothing at its far end). Some Iran servers carry the "SS fence" (`/etc/nk_ssfence.nft`): it DROPS connections to the Shadowsocks ports (1820-1829, 1840-1841) from every address except the known ones - and the probe's own connection from the server to itself too. The probe then waited six seconds, was killed, and was read as "closed": the Doctor told that the port "carries nothing" on tunnels that were healthy, started its repair for it, and called the move for quality with a speed of 0 Mb/s ("it gives 0 Mb/s") - and every such move was stopped at the end by the same false answer ("the new tunnel carries nothing"): five builds and removals of a whole tunnel in a day, nothing healed. Now a connection that gets no answer within six seconds is `NOANSWER`: nothing is known, so nothing is told, repaired or moved for it; a connection that is really closed at once, or refused, counts as before.

## A protected tunnel that loses packets (1.69.271)

A PROTECTED tunnel (the owner's mark: the Doctor never moves, rebuilds, replaces or removes it - the L2TP product stands on its inner addresses) used to get the whole smart repair every half hour when its link lost packets: other tunnel types were tested beside it for eight minutes, a fresh link came out clearly better, and the swap was refused because the tunnel is protected - nothing was ever healed and each run only loaded the pair. Now the ladder of a protected tunnel holds only the restart; no candidate is tested beside it, nothing is swapped, moved or rebuilt, and a degraded protected tunnel is looked at every six hours at most (a cut one is still retried at the usual pace). The look is one temporary GRE link between the same two servers (the panel's own link probe, ten pings each way, removed again): if it loses less than the tunnel's own link, the story and a warning event say that the loss belongs to THIS link (its inner network, not the route) and that a new link would cure it - the owner's call (protection off, then Relink); if it loses too, the route is poor and nothing on the tunnel would help. The tunnel itself is never touched. Found by hand on 2026-11-14: a new GRE key did not cure such a link (three keys, same loss), but a fresh link with other inner addresses - and other inner addresses on the very same link - were clean in the same minutes.

## Alerts that Telegram refuses, the mass disruption, the chronic look, the duel's evening (1.69.269)

Alerts: a message Telegram REFUSES (a wrong token, a blocked bot, a chat that is gone) is no longer dropped - it is kept (the newest 60, for three days) and goes out in ONE message, oldest first with their times, as soon as the bot answers; a red bar on every page says "Alerts are NOT reaching you" while it refuses (and how many wait). Mass disruption: it is declared by the offline servers that CARRY a tunnel, not by every offline server (two servers that were off for days and carried nothing had frozen the repair of a real cut). Chronic look: a tunnel cut eight times in 7 days, three of them in the last 24 hours, is moved to a steadier Iran server (the move for quality, never to a server with a chronic tunnel; one a day for the panel) and told; a server with two chronic tunnels says so. Duel: an upgrade needs one of its three rounds in the evening peak (20:00-24:00 Tehran) and the change itself starts only in the quiet hours (01:00-07:00).

## The duel (1.69.268)

Every tunnel has a warm standby of another type beside it, up and carrying nobody - a free laboratory. Every five minutes the Doctor takes ONE round for ONE tunnel: the tunnel and its standby are measured one after the other through their own test doors (two light connections, 120 MB at most each; the order alternates). Rounds are 40 minutes apart. A standby that is not at least 1.2 times as fast in the first round ends the case (nothing more is tested for it for three days); after three rounds it is better only when its median gives what the upgrade rule always asked (1.5 times and 50 Mb/s more), it was clearly faster in every round, lost at most 1 % and answers about as fast. Then the Doctor starts its own change of type without a cut, with every rail of it (once in 24 hours per tunnel, one change an hour for the whole panel, never a protected tunnel, the users watched for six hours afterwards); at most two changes a day start from duels. Nothing runs while a failover is on, while the servers carry users, or while the day's volume of the Doctor's tests is used to its routine share. The capacity tip of the tunnel tells the duel ("DUEL against its standby ..."); the switch is the settings document `duel` (`on`).

## Wire meter (1.69.266)

What a tunnel costs on the wire against what its users move, measured on the real traffic and shown in the tunnel's window and in the tip of its bandwidth bar ("Wire cost: 1.12x the users' bytes, last 24 h; this type is designed for 1.08x"). Every ten minutes the panel reads each Iran server that carries a measurable tunnel three times, eight seconds apart (one light read-only command, `wire_counters`): the users' own TCP connections to the forwarded ports against the tunnel's own side - the card of a GRE-type link plus the header it adds per packet, or the tunnel's own TCP connections for a BackPack / Chisel proxy. A ring of the last 24 hours is kept (`wiremeter` settings document) and the ratio is all the wire bytes over all the users' bytes, given once the users have moved 50 MB. A tunnel that only has a UDP / KCP / raw-socket carrier has no counter on its tunnel side and keeps the model of its type. The number is a little high by design (connections that opened and closed between two reads are lost) and holds the 3 - 8 % that the acknowledgements and inner headers of the users' own TCP cost in every tunnel. It only tells: no decision of the Doctor reads it.

## The Iran server is looked at first (1.69.294)

The Doctor tells **three** things apart for an Iran server, in this order: (1) it is **off** - the pulse gets no answer from the panel's host and nobody inside Iran sees it; its tunnels move after one minute; (2) it is **on but cut
from abroad** - the panel's host cannot connect, somebody inside Iran sees it; its tunnels move after one minute when they are down; (3) it is **on and reachable but cut off in itself** - the panel can ask it, but its own pings reach neither
the internet anchors nor the foreign servers (`netwatch.is_netcut`); its tunnels move after one minute too. In all three, nothing is restarted, rebuilt or tried against it: the guard every repair step asks (`tunnels.servers_off`)
answers for the third case as it did for the first. A tunnel that is down earns its Iran server a quick look (`netwatch.quick_look`, at most one per 45 seconds per server) at the first moment, so the verdict does not wait for the round of
five minutes. When most Iran servers are cut off together it is the line of the country and nothing moves.

## BackPack 2 and the direct types it cannot run (1.69.295)

BackPack 2.0.0 removed the UDP and QUIC carriers of its direct tunnel and made its direct PCK a port forwarder without an interface. The panel therefore never offers, picks or builds `bpd:udp`, `bpd:quic` or `bpd:pck`
(`license.RETIRED_KINDS`, asked through `license.tunnel_kind_allowed` by every place that chooses a type); the Doctor's order and its readiness for a cut leave them out; a build asked for by hand is refused with the
reason. The reverse BackPack transports and BackPack Direct · xDi are as before. Running the BackPack binary by hand on a server (anything but `-v` or `-c <file>`) opens its menu, which installs its own web panel
(port 7777) and monitor services: the panel never does that, and neither should a person.
